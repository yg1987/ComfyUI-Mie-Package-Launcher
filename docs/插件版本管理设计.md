# ComfyUI 插件版本管理实施设计

## 1. 文档信息

| 项目 | 决定 |
|---|---|
| 状态 | 可实施 |
| 首个交付版本 | v1.0 |
| 页面名称 | 插件管理 |
| 管理对象 | 便携包 `<comfyui_root>/ComfyUI/custom_nodes` 的**直接子目录** |
| 支持范围 | 已安装插件的扫描、检查、依赖预检、安全更新；以 Git HTTPS 仓库 URL 安装新插件；卸载插件目录 |
| 明确不做 | 市场、插件禁用、任意安装脚本执行、自动 stash/rebase/普通 merge、凭据管理、卸载时清理 Python 依赖 |

本设计以安全为先：不覆盖用户文件、不猜测分支、不把 Git 网络检查伪装成只读操作。所有 Git 命令必须以参数列表执行，禁止 `shell=True`。

## 2. 目标与非目标

### 2.1 目标

- 在启动器左侧导航增加独立的“插件管理”页面。
- 识别 `custom_nodes` 下的 Git、非 Git 和异常目录。
- 显示可操作的 Git 状态，并以明确原因阻止危险更新。
- 支持单个检查、全部检查、单个更新和批量更新；一次插件更新包含代码与依赖两个组成部分。
- 支持以合法的 Git HTTPS 仓库 URL 安装新插件；安装与更新使用同一套全局依赖解析、wheel 准备、离线安装与回退事务。
- 支持卸载 `custom_nodes` 的直接子目录；卸载只删除插件目录，绝不检测或删除 Python 依赖、模型、缓存或其他仓库外文件。
- 更新成功必须表示目标代码已快进、目标依赖已满足且环境校验通过；不提供“仅更新代码”。
- 批量更新只执行 Git 与依赖均通过安全预检的插件；任一插件失败不影响其余插件。
- 复用已解析的 Git 路径、Windows 隐藏进程、日志、`dubious ownership` 修复策略和 ComfyUI 进程状态。

### 2.2 非目标

- 不管理嵌套仓库、Git submodule、符号链接/联接到 `custom_nodes` 外的插件目录。
- 不自动选择 Release、tag、默认分支或 detached HEAD 的目标分支。
- 不自动执行插件的 `install.py`、任意 shell 脚本或其他自定义安装脚本。
- 不支持市场、搜索、推荐、插件禁用、SSH/本地路径仓库安装或覆盖已存在的插件目录。
- 不自动执行降级、修改保护包、解决不兼容约束、非标准来源或源码构建；在完整插件集合的约束仍可满足时，允许升级非保护包。
- 不保存或展示远程 URL 中的用户名、密码、token 等敏感信息。
- 不保证更新后正在运行的 ComfyUI 立即加载新代码；更新成功后必须重启 ComfyUI。

## 3. 现有工程约束与实施结论

### 3.1 已确认的现有结构

- ComfyUI 根目录来自 `app.config["paths"]["comfyui_root"]`；实际仓库目录为 `<comfyui_root>/ComfyUI`。
- 主窗口的页面、导航按钮、`QStackedWidget` 注册均在 `ui_qt/qt_app.py` 集中完成。
- 服务由 `services/di.py` 的 `ServiceContainer.from_app()` 创建并通过 `app.services` 提供。
- `VersionService` 已有 Git 路径替换、隐藏子进程、`dubious ownership` 重试、单进程取消和网络锁，但它维护单个 `_current_process`，**不能直接用于多个插件的并发任务**。
- `utils.common.run_hidden()` 已提供 Windows 隐藏窗口及统一日志能力；`GitService.fix_unsafe_repo()` 已可处理 Git 的 ownership 报错。
- `utils.pip.install_requirements_file()` 已提供便携包 Python、PyPI 镜像、逐包结果和忽略包能力；`services.update_service.FROZEN_PKGS` 已保护 `torch`、`torchvision`、`torchaudio`、`triton`、`xformers` 和 `numpy`。插件更新需复用这些配置与保护名单，但不能直接复用当前“逐包安装”的事务语义，因为批量插件必须先统一解析依赖冲突。

### 3.2 设计决定

1. 新增 `PluginService`，不修改 `VersionService.upgrade_latest()` 的 ComfyUI 本体更新逻辑。
2. 新增插件专用的 `PluginTaskController`，维护本批次取消事件、活动子进程集合和每仓库锁；不复用 `VersionService` 的私有 `_current_process` / `_cancel_event`。
3. v1 的批量**检查与更新均串行执行**，最大并发数固定为 1。这样可复用现有 Git 网络环境、使取消语义确定，并避免多个插件同时占用网络/认证弹窗。以后若需要并发，必须先实现每仓库独立的进程/取消管理，再将检查并发上限设为 3；更新仍保持串行。
4. 页面打开时只执行一次本地扫描，不自动联网；用户点击“刷新”后重新扫描目录，并检查所有可检查 Git 插件的远程更新。
5. 更新前 ComfyUI 必须处于未运行状态。若 `app.services.process` 报告运行中，更新按钮禁用并提示“请先停止 ComfyUI”；本地扫描和检查更新仍可用。
6. 不持久化“上次检查结果”。页面关闭或重新扫描后状态以本次结果为准，避免旧网络状态被误认为当前状态。
7. 插件更新是“依赖准备在前、Git 快进在后”的组合事务。依赖解析以所有已安装插件为全局边界，而不是按点击顺序逐插件安装；依赖阶段在第一个 Git 快进前失败或取消时，必须按第 6.4.5 节受控恢复环境。某个仓库在已有其他仓库成功快进后失败时，不回退已成功插件及其共享依赖，但必须逐项报告结果。
8. 不提供“仅更新代码”入口。无法安全自动处理依赖的插件在单条和批量更新中均跳过，并显示精确原因。
9. ComfyUI-Manager 仅作为行为和兼容策略的调研参考：实现不得导入其代码、调用其 API/CLI、读取其配置或要求用户安装它；本功能在未安装 ComfyUI-Manager 时必须完整可用。
10. 安装只接受用户手动粘贴的、去除前后空白后以 `.git` 结尾的 HTTPS Git URL；仓库名称是 URL 的最后一段去除 `.git`，且必须是可作为直接子目录名的非空值。目标目录已存在时拒绝安装，不覆盖、不合并、不替换。
11. 安装、更新和卸载前 ComfyUI 都必须处于停止状态；初次本地扫描和远程更新检查不受此限制。

## 4. 路径、发现与安全边界

### 4.1 路径解析

```python
portable_root = Path(app.config.get("paths", {}).get("comfyui_root") or ".").resolve()
comfy_root = portable_root / "ComfyUI"
custom_nodes_root = comfy_root / "custom_nodes"
```

- `custom_nodes_root` 不存在时，返回空列表和页面提示“未找到 custom_nodes 目录”，不自动创建目录。
- 仅遍历 `custom_nodes_root.iterdir()` 的目录项；按目录名不区分大小写排序。
- 安装使用 `custom_nodes_root / ".launcher-staging" / <uuid>` 作为临时 clone 目录；扫描必须排除以 `.launcher-` 开头的保留目录。只能在依赖事务完成后，以同一卷上的目录 rename 将临时 clone 移入 `custom_nodes_root / <derived_name>`。
- 对每个候选项使用 `candidate.resolve()`。仅当 `candidate_resolved.parent == custom_nodes_root.resolve()` 时处理；否则标记为 `OUTSIDE_CUSTOM_NODES` 且不可操作。此规则阻止对符号链接、junction 或 `.git` 指向外部工作树的意外写入。
- 卸载前必须重新解析用户确认的候选路径，并再次验证其 `parent == custom_nodes_root.resolve()`。任何越界、符号链接、junction 或验证失败均拒绝删除。
- Git 返回的 `--show-toplevel` 必须等于 `candidate_resolved`；不同则标记为 `NESTED_OR_EXTERNAL_REPO` 且不可操作。

### 4.2 Git 仓库识别

不得通过是否存在 `.git` 判断仓库有效性。对每个候选目录执行：

```bash
git -C <candidate> rev-parse --is-inside-work-tree
git -C <candidate> rev-parse --show-toplevel
```

首条命令输出不是 `true` 时为非 Git 安装；命令返回非零且错误不是“非仓库”时为 `REPOSITORY_ERROR`。第二条命令的路径不等于候选目录时拒绝管理，避免把父仓库或外部工作树当作插件更新。

## 5. 数据模型与状态机

### 5.1 领域对象

`services/plugin_service.py` 使用 `dataclass` 定义以下对象；页面不得自行拼接或解析 Git 输出。

```python
class PluginState(str, Enum):
    LOCAL_ONLY = "local_only"            # 尚未联网检查
    UP_TO_DATE = "up_to_date"
    UPDATE_AVAILABLE = "update_available"
    LOCAL_CHANGES = "local_changes"
    LOCAL_AHEAD = "local_ahead"
    DIVERGED = "diverged"
    DETACHED_HEAD = "detached_head"
    NO_UPSTREAM = "no_upstream"
    NO_REMOTE = "no_remote"
    NON_GIT = "non_git"
    UNBORN_HEAD = "unborn_head"
    REPOSITORY_ERROR = "repository_error"
    OUTSIDE_CUSTOM_NODES = "outside_custom_nodes"
    NESTED_OR_EXTERNAL_REPO = "nested_or_external_repo"
    SUBMODULES_UNSUPPORTED = "submodules_unsupported"
    CHECK_FAILED = "check_failed"
    UPDATE_FAILED = "update_failed"
    REMOVED = "removed"                # 仅用于卸载成功的结果记录；不再作为列表行
    CANCELLED = "cancelled"

class UpdateAvailability(str, Enum):
    UNKNOWN = "unknown"                 # 尚未检查远程
    CHECKING = "checking"
    UP_TO_DATE = "up_to_date"
    AVAILABLE = "available"             # 远程有本地尚未包含的提交
    NOT_CHECKABLE = "not_checkable"
    CHECK_FAILED = "check_failed"

class DependencyState(str, Enum):
    UNKNOWN = "unknown"
    CHECKING = "checking"
    NOT_CHANGED = "not_changed"
    SATISFIED = "satisfied"
    SAFE_TO_INSTALL = "safe_to_install"
    COMPATIBLE_UPGRADE = "compatible_upgrade"
    INCOMPATIBLE_CONSTRAINTS_BLOCKED = "incompatible_constraints_blocked"
    DOWNGRADE_BLOCKED = "downgrade_blocked"
    GLOBAL_INDEX_INCOMPLETE = "global_index_incomplete"
    PROTECTED_PACKAGE_BLOCKED = "protected_package_blocked"
    NON_STANDARD_SOURCE_BLOCKED = "non_standard_source_blocked"
    SOURCE_BUILD_BLOCKED = "source_build_blocked"
    CUSTOM_SCRIPT_BLOCKED = "custom_script_blocked"
    PREFLIGHT_FAILED = "preflight_failed"
    INSTALLING = "installing"
    INSTALL_FAILED = "install_failed"
    READY = "ready"

@dataclass
class PluginRecord:
    name: str
    path: Path
    state: PluginState
    update_availability: UpdateAvailability = UpdateAvailability.UNKNOWN
    dependency_state: DependencyState = DependencyState.UNKNOWN
    head: str | None = None               # 完整 SHA；UI 仅显示前 12 位
    branch: str | None = None
    upstream: str | None = None           # 例如 origin/main
    remote_name: str | None = None
    remote_url_display: str | None = None # 已去凭据，仅供 UI 显示
    dirty_count: int = 0
    untracked_count: int = 0
    ahead: int | None = None
    behind: int | None = None
    checked_at: datetime | None = None
    check_generation: int = 0            # 当前页面会话内最近一次完整刷新批次号
    target_head: str | None = None        # 本轮 fetch 后精确锁定的上游提交
    dependency_additions: tuple[str, ...] = ()
    dependency_changes: tuple[str, ...] = ()  # 例如 foo: 0.1 -> 0.2
    dependency_strict_constraints: tuple[str, ...] = ()
    dependency_conflicts: tuple[str, ...] = ()  # 例如 plugin_a: foo==1 与 plugin_b: foo>=3
    dependency_reason: str = ""
    reason: str = ""
    error_code: str | None = None
    can_check: bool = False
    can_update: bool = False

@dataclass(frozen=True)
class DependencyPlan:
    plugin_path: Path
    target_head: str
    state: DependencyState
    requirements: tuple[str, ...]
    additions: tuple[str, ...]
    resolved_changes: tuple[str, ...] = ()  # 例如 foo: 0.1 -> 0.2
    protected_conflicts: tuple[str, ...] = ()
    strict_constraints: tuple[str, ...] = ()
    conflicting_plugins: tuple[str, ...] = ()
    conflicts: tuple[str, ...] = ()  # 每项包含包名、各插件名、约束和当前/计划版本
    reason: str = ""

@dataclass(frozen=True)
class PluginInstallPreview:
    source_url_display: str
    staging_path: Path
    target_path: Path
    target_head: str
    dependency_plan: DependencyPlan
    expires_at: datetime

@dataclass
class PluginOperationResult:
    plugin_name: str
    operation: Literal["scan", "check", "update", "install", "uninstall"]
    outcome: Literal["success", "skipped", "failed", "cancelled"]
    state: PluginState
    previous_head: str | None
    current_head: str | None
    dependencies_added: tuple[str, ...]
    dependencies_changed: tuple[str, ...]
    message: str
```

`PluginRecord` 是扫描、检查和更新之间唯一可传递的数据；`DependencyPlan` 是依赖服务生成的不可变计划，必须绑定插件路径和精确 `target_head`，不得复用于其他提交。`PluginInstallPreview` 仅表示已 clone 到受控临时目录、完成依赖预检但未修改 Python 环境、也未移入 `custom_nodes` 的安装候选。它只能使用一次，超时、取消、关闭页面或开始其他任务时必须删除临时目录。结果对象用于页面进度和最终摘要。完整 SHA、原始 stderr 只写入日志，不进入 UI 表格。`check_generation` 仅在内存中使用：一次“刷新”完成后递增，只有属于当前完整刷新批次、且 Git 与依赖均安全的 `UPDATE_AVAILABLE` 记录可进入更新队列。

### 5.2 状态判定优先级

状态按以下顺序判定，首个命中的状态即为最终状态。此优先级保证有风险时不会被“可更新”覆盖：

| 优先级 | 条件 | 状态 | 可检查 | 可更新 |
|---:|---|---|:---:|:---:|
| 1 | 路径越界 / Git 顶层不是候选目录 | `OUTSIDE_CUSTOM_NODES` / `NESTED_OR_EXTERNAL_REPO` | 否 | 否 |
| 2 | 不是有效 Git 工作树 | `NON_GIT` | 否 | 否 |
| 3 | Git 元数据读取失败 | `REPOSITORY_ERROR` | 可重试 | 否 |
| 4 | `HEAD` 不存在（新建但没有首个提交） | `UNBORN_HEAD` | 否 | 否 |
| 5 | 检测到 `.gitmodules` 或 `git submodule status --recursive` 有输出 | `SUBMODULES_UNSUPPORTED` | 否 | 否 |
| 6 | 工作区有已跟踪或未跟踪修改 | `LOCAL_CHANGES` | 是 | 否 |
| 7 | `HEAD` 不在本地分支 | `DETACHED_HEAD` | 否 | 否 |
| 8 | 没有远程 | `NO_REMOTE` | 否 | 否 |
| 9 | 当前分支没有 upstream | `NO_UPSTREAM` | 否 | 否 |
| 10 | `ahead > 0 and behind > 0` | `DIVERGED` | 是 | 否 |
| 11 | `ahead > 0` | `LOCAL_AHEAD` | 是 | 否 |
| 12 | `behind > 0` 且 Git 前提成立 | `UPDATE_AVAILABLE` | 是 | 仅依赖预检通过时 |
| 13 | `ahead == 0 and behind == 0` | `UP_TO_DATE` | 是 | 否 |

网络、认证、超时和取消只覆盖本次检查/更新的执行结果：分别为 `CHECK_FAILED`、`UPDATE_FAILED`、`CANCELLED`，并在 `reason` 中保留上一项可理解的风险上下文。检查失败后 `can_update` 必须为 `False`。

`PluginState` 表示仓库的综合安全状态，`UpdateAvailability` 专门回答“远程是否有更新”，两者不得混为一个字段：

- 未执行刷新时，可检查 Git 插件为 `UNKNOWN`；无 remote、无 upstream、detached、非 Git 等为 `NOT_CHECKABLE`。
- fetch 和 ahead/behind 计算成功后，`behind > 0` 为 `AVAILABLE`，否则为 `UP_TO_DATE`。
- 因此有本地修改或已经分叉的插件仍可显示 `AVAILABLE`，但 `can_update=False`，页面文案为“有更新，需手动处理”。
- 只有 `update_availability == AVAILABLE` 且综合状态满足干净分支、ahead=0 等全部安全条件时，`state` 才是 `UPDATE_AVAILABLE` 且 `can_update=True`。
- 检查异常为 `CHECK_FAILED`；刷新期间的 `CHECKING` 属于运行时状态，不持久化。

`DependencyState` 表示目标提交的依赖是否能由启动器安全处理。`can_update=True` 必须同时满足 Git 安全条件和 `dependency_state in {NOT_CHANGED, SATISFIED, SAFE_TO_INSTALL, COMPATIBLE_UPGRADE}`；任何 `*_BLOCKED`、`GLOBAL_INDEX_INCOMPLETE`、`PREFLIGHT_FAILED` 或 `INSTALL_FAILED` 状态均阻止整个插件更新。

## 6. Git 命令契约

### 6.1 公共执行规则

- 所有命令以 `list[str]` 传给 `subprocess` / `run_hidden`；`cwd=record.path`。
- 若首个参数为 `git`，替换为 `app.git_path`；为空时先调用 `app.services.git.resolve_git()`，解析失败则所有 Git 项显示“未找到 Git”。
- 默认文本编码为 UTF-8、`errors="replace"`；超时分别为本地命令 10 秒、`fetch` 60 秒、`merge --ff-only` 120 秒。
- 若 stderr 包含 `dubious ownership`，调用 `app.services.git.fix_unsafe_repo(str(path))` 一次后重试原命令一次；仍失败则返回错误，不继续修改全局 Git 配置。
- 日志记录插件名、动作、退出码和经脱敏后的错误摘要；原始 remote URL、命令行凭据、token 均不可写入日志或界面。

### 6.2 本地扫描（不联网，不写工作树）

对有效 Git 插件依次执行：

```bash
git status --porcelain=v1 -z --untracked-files=all
git rev-parse --verify HEAD
git branch --show-current
git remote
git remote get-url <remote_name>
git rev-parse --abbrev-ref --symbolic-full-name @{upstream}
git submodule status --recursive
```

实现细节：

- 用 NUL 分隔输出统计 `dirty_count`、`untracked_count`，不要通过自然语言 `git status` 解析。
- 分支为空即 `DETACHED_HEAD`；不可因此猜测 `main`、`master` 或远程默认分支。
- 当前分支存在时，优先读取其 `@{upstream}`；`remote_name` 取 upstream 的 `<remote>/` 前缀。没有 upstream 时仅显示 `origin` 的脱敏 URL（如存在），但不能据此更新。
- `sanitize_remote_url()` 必须移除 URL 的 `userinfo`、查询参数和 fragment。例如 `https://token@host/org/repo.git` 显示为 `https://host/org/repo.git`；SSH URL 仅显示 `host:path`，不显示用户名。
- 本地扫描成功但尚未 fetch 的可更新候选为 `LOCAL_ONLY`，列表显示“未检查远程”，不能更新。

### 6.3 检查更新（允许写 Git 元数据，不写工作树）

只对 `can_check=True` 的 Git 插件运行；逐项串行：

```bash
git fetch --prune <remote_name>
git status --porcelain=v1 -z --untracked-files=all
git rev-list --left-right --count HEAD...@{upstream}
```

- `fetch` 会更新 `.git` 内的远程跟踪引用，不会修改插件工作区；UI 文案必须使用“检查远程更新”，不要声称“完全不修改仓库”。
- `rev-list` 输出必须恰为两个非负整数：左侧为 ahead，右侧为 behind。输出不合法即 `CHECK_FAILED`。
- fetch 后重新读取工作区状态。若此时产生本地修改，状态改为 `LOCAL_CHANGES`，不允许更新。
- 对 `behind > 0` 的插件记录精确 `target_head = rev-parse @{upstream}`，并执行第 6.4 节的依赖预检。只有 Git 与依赖预检均通过时才设置 `can_update=True`。
- “刷新”检查全部插件时，单项失败继续处理下一个插件；用户取消后不再启动下一项，并将尚未检查的 Git 插件恢复为 `LOCAL_ONLY`，显示“未检查”。

### 6.4 依赖预检与准备

#### 6.4.1 成功边界

插件更新与安装都不可拆分为用户可选的“代码”和“依赖”步骤。启动器不提供“跳过依赖继续”入口：

1. 候选 `target_head` 的依赖声明已被识别；
2. 目标依赖已经满足，或全局 resolver 已证明可在不改变保护包、不中断任何已安装插件约束、且不降级的前提下安装或升级；
3. 依赖安装完成，且没有引入新的 `pip check` 错误；
4. 更新时插件 Git 仓库快进到本轮锁定的 `target_head`；安装时临时 clone 以同一卷 rename 移入预定的目标目录；
5. 最终再次验证目标依赖全部满足。

任一条件失败都不能显示成功。依赖预检失败发生在更新的 Git 快进和安装的目录落位前：更新必须保留旧插件代码，安装必须不留下新插件目录。

#### 6.4.2 支持的依赖声明

v1 自动处理：

- 仓库根目录 `requirements.txt`；
- `requirements.txt` 通过 `-r relative/path.txt` 引用的仓库内相对文件；
- `pyproject.toml` 中静态的 `[project].dependencies` 与 `[project.optional-dependencies]` 不自动安装，只有基础 dependencies 进入计划。

读取的必须是候选仓库本轮 `target_head` 中的文件；更新时不得读取更新前工作区文件，安装时不得读取仓库的浮动远程状态。

```bash
git cat-file -e <target_head>:requirements.txt
git show <target_head>:requirements.txt
git cat-file -e <target_head>:pyproject.toml
git show <target_head>:pyproject.toml
git cat-file -e <target_head>:install.py
git cat-file -e <target_head>:setup.py
git cat-file -e <target_head>:setup.cfg
```

- 递归 `-r` 最大深度为 5；规范化路径必须仍位于仓库内，绝对路径、`..` 越界和循环引用均阻止更新。
- requirements 中除仓库内相对 `-r` 之外的 pip 命令行选项一律阻止自动更新，不能允许插件覆盖启动器的 index、trusted-host、constraint 或安装模式。
- 使用 `packaging.requirements.Requirement` 解析包名、extras、specifier 与 environment marker；marker 必须按便携包 Python 的实际环境求值，不能像现有简化解析器一样直接丢弃。
- `pyproject.toml` 使用标准库 `tomllib`（旧 Python 使用项目已有兼容依赖）；`dynamic` 包含 `dependencies` 时无法静态判断，阻止更新。

以下任一情况阻止整个自动更新或安装，并设置对应 `DependencyState`：

| 条件 | 状态 | 页面提示 |
|---|---|---|
| 全局 resolver 找不到同时满足所有已安装插件约束的版本 | `INCOMPATIBLE_CONSTRAINTS_BLOCKED` | `依赖约束不兼容`，展示涉及插件、包名、各自约束和 resolver 摘要 |
| resolver 计划将任一非保护包降级 | `DOWNGRADE_BLOCKED` | `依赖需要降级，已阻止`，展示 `包名：当前版本 → 计划版本` |
| 任一已安装插件的依赖声明无法静态读取，且本次计划会改动共享包 | `GLOBAL_INDEX_INCOMPLETE` | `无法完整验证其他插件兼容性`，展示未纳入索引的插件及原因 |
| 目标要求改变保护包版本 | `PROTECTED_PACKAGE_BLOCKED` | `核心依赖受保护`，展示包名、当前版本和目标约束 |
| VCS URL、HTTP 直链、本地路径、editable 或仓库外 include | `NON_STANDARD_SOURCE_BLOCKED` | `包含非标准依赖源，无法安全自动安装`，展示脱敏后的依赖项 |
| 解析结果需要 sdist/本地编译且无兼容 wheel | `SOURCE_BUILD_BLOCKED` | `依赖需要源码构建，无法安全自动安装`，展示包名和目标版本 |
| 目标提交存在 `install.py`、动态依赖或其他自定义安装脚本 | `CUSTOM_SCRIPT_BLOCKED` | `包含自定义安装脚本，启动器不会自动执行` |
| 依赖文件语法、resolver、镜像或网络检查失败 | `PREFLIGHT_FAILED` | `依赖预检失败`，展示可读错误和重试提示 |

`services.update_service.FROZEN_PKGS` 是最低保护集合；插件依赖服务直接导入/复用该集合，不能复制出第二份易漂移的名单。保护包当前版本已满足目标约束时允许继续，但绝不自动改变其版本。

`==`、`<`、`<=`、`~=` 与 `!=` 不是“错误操作符”，也不因出现而自动阻止更新；它们只是比宽松下界更容易限制可选版本，必须在页面中突出显示为“严格约束”。同样，`>=` 也不是自动安全的承诺：最终是否安全只由对所有已安装插件约束的语义解析和 resolver 结果决定，不能用字符串比较或只看某一个操作符作判断。实现必须用 `packaging.requirements.Requirement`、`SpecifierSet` 和 `Version` 处理 PEP 440 语义。

预检以 resolver 的**实际计划版本**为准，且必须把结果逐插件写回。例如当前环境有 `a==3` 时，候选插件要求 `a>=1`，计划版本仍为 `3`，该依赖为 `SATISFIED`，不下载、不安装也不改变环境；候选要求 `a==1` 时，计划版本会变为 `1`，属于降级，必须以 `DOWNGRADE_BLOCKED` 阻止该候选。候选要求更高版本时，只有计划版本仍满足全部既有插件约束且不触及保护包，才可标记为 `COMPATIBLE_UPGRADE`。

#### 6.4.3 全局依赖索引与统一解析

刷新时对有远程更新的插件执行以下只预检流程，不修改 Python 环境：

1. 建立**全局依赖索引**：枚举 `custom_nodes` 下全部已安装插件。Git 插件从当前 `HEAD` 的 Git 对象读取静态声明；非 Git 插件只读取其当前目录中的标准声明，绝不执行其中代码。对于更新候选，以已锁定的 `target_head` 声明替换其当前声明；对于安装候选，将临时 clone 的已锁定 `target_head` 声明作为一条新索引项加入集合；其他插件继续使用当前声明。索引项记录 `plugin_path`、声明来源、规范化后的 `Requirement`、marker 求值结果、解析状态和不可静态判断原因。
2. `install.py`、动态依赖、非法声明或其他不可解析来源的插件也必须进入索引并标为“不完整”。它不影响“无需安装/升级依赖”的代码更新；一旦候选计划要改动共享包，存在任何不完整索引项即按 `GLOBAL_INDEX_INCOMPLETE` 阻止，不能假设未知插件兼容。
3. 以 `importlib.metadata` 记录当前安装包的规范化名称与精确版本，并运行一次基线 `python -m pip check`。该快照只用于差异、回退和诊断，**不得**把所有包固定成 constraints。
4. 仅为 `FROZEN_PKGS` 写入精确版本 constraints；把全局索引中的有效 requirements 汇总为 `combined.txt`，使用便携包 Python 执行：

   ```bash
   <portable-python> -m pip install --dry-run --report <plan.json> \
     --upgrade-strategy only-if-needed \
     -r <combined.txt> -c <protected-constraints.txt>
   ```

   不传 `--upgrade`，避免仅因宽松的 `>=` 声明而将已满足的直接依赖升级到最新版本；当新约束确实不满足时，resolver 仍可选择所需的更高版本。
5. 从 report 生成每个包的精确 `当前版本 → 解析版本`、来源 wheel、涉及插件和严格约束标记。解析版本等于当前版本为 `SATISFIED`；只新增包为 `SAFE_TO_INSTALL`；存在非保护包升级且满足所有全局约束为 `COMPATIBLE_UPGRADE`；降级、保护包变更、不可兼容约束、sdist 或非标准来源分别阻止。批量任务对每个候选都必须单独生成结果：若某候选导致降级或保护包变更，写入该候选的 `dependency_conflicts`，包含包名、当前/计划版本、候选约束和受影响的既有插件约束；只阻止该候选及同一冲突组中的候选，不得笼统阻止整个批次。
6. resolver 失败时，使用同一份全局索引做最小冲突分组/逐插件解析以定位责任插件；不能因一个冲突插件让无关插件都失去明确状态。批量刷新或更新必须把冲突回写到**每个候选插件行**：冲突行的 `dependency_conflicts` 至少包含“包名、当前版本、计划版本、候选插件名及与其冲突的已安装/候选插件名和约束”，`conflicting_plugins` 只保存相关插件名。冲突组中的候选设为 `INCOMPATIBLE_CONSTRAINTS_BLOCKED` 或 `DOWNGRADE_BLOCKED` 且不可更新；排除这些候选后，必须对其余候选重新解析，仍安全的插件保持可更新。单条更新也必须使用全局索引，不能只用被点击插件的 requirements。
7. 下载项必须是适配当前 Python/平台的 wheel。将 report 的完整精确解及 wheel 的 SHA-256 写为本批次临时 lock；它是后续离线安装的唯一输入。

刷新期间所有候选记录的 `can_update` 暂时保持 `False`。逐插件预检结果可以实时展示，但只有完整集合的聚合 resolver 完成、跨插件冲突已经回写后，才能生成新的 `check_generation` 并启用更新按钮。

安装预检不依赖“刷新”批次：先完成临时 clone、路径边界、有效 Git 工作树、干净工作区、精确 `HEAD` 和无 submodule 验证，再把它加入同一全局索引完成 resolver。这一阶段不修改 Python 环境、不写入最终插件目录；成功后产出只能使用一次的 `PluginInstallPreview`，供用户确认精确依赖计划。

`pip freeze`、当前版本快照、保护包 constraints、`pip check` 基线和 resolver report 只用于预检、诊断、受控回退和结果展示，不得宣传为可完整恢复环境的备份。ComfyUI-Manager 的 pip 快照与修复机制可以作为兼容案例参考，但本实现不调用也不依赖它。

#### 6.4.4 提交代码前的依赖准备

对通过预检的单条或批量更新，以及用户确认的安装预览：

1. 锁定本轮候选集合、每个插件的 `target_head` 和依赖计划；任务期间不得接受新的刷新/更新/安装/卸载请求。
2. 将 forward lock 中所有 wheel（包括新增和将升级的包）以及所有将被替换包的**当前精确版本** wheel 下载到本批次临时 wheelhouse；记录更新前精确版本和更新前不存在的包。任一下载失败时不修改环境或 Git。
3. 以一个聚合安装命令从本地 wheelhouse 安装精确 forward lock，禁止联网补包：

```bash
<portable-python> -m pip install \
  --no-index --find-links <wheelhouse> \
  --require-hashes -r <forward.lock>
```

4. 再次逐插件检查目标 requirements 是否满足，并将 `pip check` 与基线逐条比较。只要出现本轮前不存在的新环境错误，依赖阶段整体失败，所有尚未提交代码的更新保持旧版本，安装候选保留在临时目录中。
5. pip 安装、依赖复验或环境校验失败/取消时，在任何候选完成 Git 快进或安装目录落位前，必须执行第 6.4.5 节的受控依赖回退；不能把“已新增但本次插件未交付”的依赖留在环境中。
6. 仅依赖验证通过的更新候选进入第 6.5 节的 Git 快进；仅依赖验证通过的安装候选进入第 6.6 节的目录落位。

#### 6.4.5 受控依赖回退

依赖安装会修改共享环境，因此必须具备有限、可验证的回退能力，而不是把“当前环境 constraints”误当作备份：

1. 仅在本批次尚未有任何候选完成 Git 快进或安装目录落位时允许自动回退；一旦已有插件成功交付，依赖变更可能已被其使用，后续失败按单插件失败处理，不回退共享环境。
2. 回退只操作 forward lock 实际改动过的包：对原先存在的包，使用 wheelhouse 中的 previous lock 离线重装其精确旧版本；对原先不存在、由本批次新增的包，执行精确名单的 `pip uninstall -y`。禁止按目录、glob 或 `pip freeze` 广泛卸载。
3. 回退后必须重新验证目标包版本与更新前快照一致，并执行 `pip check`；只允许恢复到更新前的基线问题集合，不得引入新的问题。
4. 回退成功时，所有更新候选保持旧 `HEAD`，所有安装候选删除临时 clone，结果显示“依赖阶段已回退，插件未交付”。回退失败时立即停止自动操作，标记 `DEPENDENCY_ROLLBACK_FAILED` / `操作未完成，需要人工修复`，展示实际 `current → resolved` 计划、回退失败包及离线修复建议；此为关键错误。

### 6.5 安全更新事务

更新只接受**刚完成本轮检查**且 `state == UPDATE_AVAILABLE`、`ahead == 0`、`behind > 0`、依赖预检通过并已准备完成的记录。开始 Git 阶段时再次执行前置校验，防止用户在检查后手动修改仓库：

```bash
git status --porcelain=v1 -z --untracked-files=all
git branch --show-current
git rev-parse --abbrev-ref --symbolic-full-name @{upstream}
git rev-list --left-right --count HEAD...@{upstream}
git rev-parse @{upstream}
git merge --ff-only <target_head>
git rev-parse HEAD
git rev-list --left-right --count HEAD...@{upstream}
```

规则：

- 前置校验任一条件变化，跳过该插件并刷新为当前状态；其余已锁定插件仍可继续。若本批次最终没有任何插件成功快进，则在任务收尾按第 6.4.5 节回退本批次共享依赖；只要已有插件成功快进，依赖即保留以保证已成功插件可用。
- 当前 `@{upstream}` 必须仍等于记录的 `target_head`。不在更新路径执行 `fetch` 或 `pull`；只用 `git merge --ff-only <target_head>` 快进到刚检查并完成依赖预检的精确提交。
- `merge --ff-only` 失败时 `HEAD` 未变化，绝不尝试 rebase、普通 merge、stash、checkout、reset 或删除分支。
- `HEAD` 必须从更新前提交变化到精确 `target_head`。快进后再次验证目标依赖；验证通过才记录“已更新 `old_short` → `new_short`”并将状态设为 `UP_TO_DATE/READY`。
- 快进后若发生理论上不应出现的依赖复验失败，仅当工作区仍干净、当前分支仍等于任务开始分支、`HEAD == target_head` 且 reflog 证明上一动作是本任务快进时，才允许执行 `git reset --hard <previous_head>` 并复验。这是唯一允许 reset 的受控回退，只用于恢复本任务刚完成的快进；任一守卫不成立时停止自动操作并显示“更新未完成，需要人工修复”，不得覆盖用户修改。
- 未开始项因取消、ComfyUI 已启动或状态不符合条件而不执行时，结果为 `skipped`，不是失败。

### 6.6 安全安装事务

安装只接受用户在安装输入框中粘贴的 HTTPS Git URL，且 URL 路径必须以 `.git` 结尾。不支持 SSH、`file://`、本地路径、平台项目页面 URL，URL 也不得包含用户名、密码或 token。每次安装按以下流程执行：

1. 去除输入首尾空白并解析 URL。仓库目录名取 URL 最后一段并去除 `.git`；名称必须非空，不得为 `.`、`..`、保留设备名、含路径分隔符或 Windows 非法字符。规范化后的目标路径必须是 `custom_nodes` 的直接子目录。
2. 在执行 Git 前验证 `custom_nodes` 已存在、目标目录不存在、ComfyUI 已停止且任务控制器空闲；任一条件不满足均直接失败，不创建或覆盖目标目录。
3. 使用 `git clone --no-recurse-submodules <url> <staging_path>` 克隆到第 4.1 节定义的保留临时目录。命令使用参数列表且对 URL 和输出脱敏；取消、超时或 clone 失败时删除该临时目录。
4. 对临时 clone 重新验证有效 Git 工作树、顶层目录一致、工作区干净、精确 `HEAD` 存在且不含 `.gitmodules` / submodule。将该 `HEAD` 锁定为 `target_head`；任何验证失败都删除临时 clone，绝不落位。
5. 按第 6.4.2、6.4.3 节读取 `target_head` 的静态依赖声明，将候选插件作为新索引项加入全部已安装插件的全局依赖集合。预检阶段不修改 Python 环境、不写入最终插件目录；成功后生成一次性的 `PluginInstallPreview`。
6. UI 展示仓库脱敏 URL、精确提交、最终目录、新增/升级依赖、严格约束和风险。只有用户再次确认后才按第 6.4.4 节准备 wheel、离线安装并校验；不提供“跳过依赖继续安装”。
7. 依赖事务成功后，重新验证目标目录仍不存在、临时 clone 仍干净且 `HEAD == target_head`，再使用同卷目录 rename 原子移入目标目录。rename 失败时删除临时 clone，并在尚无插件交付成功的前提下按第 6.4.5 节回退依赖；不允许用 copy 作为降级方案。
8. 落位后重新读取目标声明并验证依赖全部满足、`pip check` 相对基线无新增错误，随后重新本地扫描并把插件加入列表。最终复验异常时停止自动操作并提示人工修复，不自动删除已经成功落位的插件。

### 6.7 卸载事务

卸载不是依赖事务：它不读取、解析、安装或卸载 Python 包，也不检查或删除模型、缓存、配置及 `custom_nodes` 之外的任何文件。仅能对最近一次本地扫描得到的直接子目录执行：

1. ComfyUI 必须停止且任务控制器必须空闲。页面先显示插件名、规范化绝对路径、目录将被永久删除以及“Python 依赖不会删除”；用户明确确认后才继续。检测到本地修改或未跟踪文件时额外显示数量，但不阻止用户明确卸载。
2. 删除前按第 4.1 节重新解析并验证路径仍是 `custom_nodes` 的直接子目录，且不是符号链接或 junction。任一验证失败均拒绝删除。
3. 只递归删除该已验证目录。删除开始后禁用取消；文件系统报错时立即停止并重新扫描实际剩余状态，不继续操作其他目录。
4. 删除成功后从表格和内存集合移除记录，并返回 `operation="uninstall"`、`state=REMOVED` 的结构化结果。卸载后不触发 pip、Git 网络命令或自动远程刷新。

### 7.2 `PluginService` 公共接口

```python
class PluginService:
    def scan_local(self) -> list[PluginRecord]: ...
    def refresh_all(
        self,
        cancel: threading.Event,
        on_progress: Callable[[PluginOperationResult, int, int], None],
    ) -> list[PluginRecord]: ...
    def check_one(self, record: PluginRecord, cancel: threading.Event) -> PluginRecord: ...
    def check_many(
        self,
        records: Sequence[PluginRecord],
        cancel: threading.Event,
        on_progress: Callable[[PluginOperationResult, int, int], None],
    ) -> list[PluginOperationResult]: ...
    def update_one(self, record: PluginRecord, cancel: threading.Event) -> PluginOperationResult: ...
    def update_many(
        self,
        records: Sequence[PluginRecord],
        cancel: threading.Event,
        on_progress: Callable[[PluginOperationResult, int, int], None],
    ) -> list[PluginOperationResult]: ...
    def prepare_install(
        self,
        source_url: str,
        cancel: threading.Event,
    ) -> PluginInstallPreview: ...
    def install_from_preview(
        self,
        preview: PluginInstallPreview,
        cancel: threading.Event,
        on_progress: Callable[..., None],
    ) -> PluginOperationResult: ...
    def uninstall_one(self, record: PluginRecord) -> PluginOperationResult: ...

class PluginDependencyService:
    def build_global_index(
        self,
        installed_records: Sequence[PluginRecord],
        target_overrides: Mapping[Path, str],
        install_candidates: Sequence[PluginRecord] = (),
    ) -> GlobalDependencyIndex: ...
    def inspect_target(self, record: PluginRecord) -> DependencyPlan: ...
    def preflight_many(
        self,
        records: Sequence[PluginRecord],
        cancel: threading.Event,
    ) -> dict[Path, DependencyPlan]: ...
    def prepare_and_install(
        self,
        plans: Sequence[DependencyPlan],
        cancel: threading.Event,
        on_progress: Callable[..., None],
    ) -> DependencyInstallResult: ...
    def validate_environment(self, plans: Sequence[DependencyPlan]) -> DependencyValidationResult: ...
```

- `scan_local()` 不启动网络命令，返回完整列表，异常转换为对应记录状态，不因单目录失败而抛出整个扫描。
- `refresh_all()` 先重新扫描所有直接子目录，再依次检查所有 `can_check=True` 的 Git 插件；非 Git 及不可检查项保留本地扫描状态。仅当全部目标均已处理且未取消时，调用方才把结果设为新的完整刷新批次。
- `check_one()` 只接受当前 `PluginRecord`，在开始前重新验证路径与仓库顶层；不会信任 UI 传入的 `path` 以外字段。
- `update_many()` 内部再次过滤 `UPDATE_AVAILABLE` 和依赖安全状态，而不是信任页面状态；它必须携带本轮的全局依赖索引，先聚合调用 `prepare_and_install()`，依赖阶段成功后才逐个快进 Git。
- `prepare_install()` 完成 URL/名称/目标目录校验、临时 clone、Git 与 submodule 边界检查，并把临时候选作为 `install_candidates` 加入全局依赖索引；只返回未过期且未修改环境的 `PluginInstallPreview`。`install_from_preview()` 必须重新校验 preview、ComfyUI 状态、目标目录和 staging `HEAD`，再调用统一的 `prepare_and_install()` 与第 6.6 节落位步骤。
- `uninstall_one()` 只接受最近扫描得到的记录；它在删除前重新验证路径和 ComfyUI 停止状态，不调用 `PluginDependencyService`、pip 或 Git 网络命令。
- `PluginDependencyService` 的全局索引输入包含全部已安装插件的规范化路径；更新候选只接受锁定的 `target_head` 覆盖，安装候选从受控 staging 路径读取锁定 `target_head`，其他 Git 插件读取当前 `HEAD`，非 Git 插件只静态读取工作区声明。所有依赖文件均不得执行目标仓库中的 Python 代码。
- 所有方法返回结构化结果；页面不可依据 Git 输出字符串判断成功或失败。

### 7.3 `PluginTaskController` 与 Qt worker

`core/plugin_workers.py` 实现一个工作线程控制器（可为 `QObject + QThread` 或项目既有兼容的 worker 形式），最少提供：

```python
progress = pyqtSignal(object, int, int)  # PluginOperationResult, current, total
finished = pyqtSignal(list)              # list[PluginOperationResult]
failed = pyqtSignal(str)                 # 仅用于任务级未预期异常

start_scan()
start_refresh()
start_update(records)  # 依赖准备 + Git 快进的完整事务
start_prepare_install(source_url)  # 临时 clone + 全局依赖预检，不修改环境
start_install(preview)  # 用户确认后：依赖事务 + 目录落位
start_uninstall(record)  # 已确认后：仅删除已验证目录
request_cancel()
is_busy()
```

- 每个任务创建新的 `threading.Event` 和活动 `Popen` 注册表；`request_cancel()` 设置事件，并终止当前活动 Git 或 pip 进程。卸载开始实际删除后不再接受取消。
- worker 完成、失败或取消后必须断开/清空线程引用，恢复 UI 控件；不可遗留后台线程。
- 仅 worker 线程可执行 Git 命令；所有 Qt 控件更新通过信号在主线程完成。
- 页面退出或应用关闭时：请求取消、等待最多 3 秒；超时仅记录日志，不阻塞窗口销毁。
- `PluginInstallPreview` 等待用户确认期间不占用 worker；其 staging 目录由页面持有的预览 token 管理。用户拒绝、超过 10 分钟、页面退出、ComfyUI 启动或开始其他任务时必须在 worker 中清理该目录并使 token 失效。

### 8.3 按钮与选择规则

| 控件 | 可用条件 | 行为 |
|---|---|---|
| 安装插件 | 空闲、URL 格式有效、ComfyUI 未运行 | 先临时 clone 并生成全局依赖预览；预览通过且用户确认后，安装依赖并将目录落位。输入框内容仅保留在当前页面会话 |
| 刷新 | 空闲 | 重新扫描 `custom_nodes` 的所有直接子目录，并检查所有 `can_check=True` 的 Git 插件；作用于全部插件，不受当前页、搜索或筛选影响 |
| 全部更新（N） | 空闲、当前完整刷新批次中 Git 与依赖预检均通过的数量 N > 0、ComfyUI 未运行 | 为全部 N 个插件统一准备依赖，再逐个快进代码；不受当前页、搜索或筛选影响 |
| 行内“更新” | 空闲、该项属于当前完整刷新批次、Git 与依赖预检均通过、ComfyUI 未运行 | 为该插件准备依赖并快进代码；任一阶段失败均不算更新成功 |
| 行内“查看原因” | 该项有远程更新但依赖被阻止 | 展示阻止类型、涉及包、当前/要求版本和处理建议；不提供仅更新代码 |
| 行内“卸载” | 空闲、记录为已验证的 `custom_nodes` 直接子目录、ComfyUI 未运行 | 显示永久删除确认；确认后仅删除该插件目录，不处理依赖。可用于 Git 和非 Git 插件 |
| 取消 | worker 忙 | 请求取消；文本改为“正在取消…”且不重复触发 |

- 远程 URL 列只显示脱敏值；为空显示 `—`。
- “分支/提交”格式：`main · abcdef123456`；detached 状态仅显示 `detached · abcdef123456`。
- 默认排序：`UPDATE_AVAILABLE`、`LOCAL_CHANGES`、`CHECK_FAILED/REPOSITORY_ERROR`、其他状态；同组按插件名排序。
- 搜索匹配插件目录名和脱敏远程 URL；状态筛选为单选，默认“全部”。
- 首次切入页面后自动触发一次本地扫描，完整展示所有插件；此时 Git 插件显示“未检查”。之后仅由用户点击“刷新”发起网络检查。
- 输入 URL 后点击“安装插件”不是市场检索：只能请求用户提供的一个仓库。clone 和预检结束时，若被阻止则展示原因并清理 staging；若通过则显示第二次确认框。用户取消确认或关闭确认框时也必须清理 staging。
- 刷新开始时，先用新扫描结果替换目录列表，并将可检查 Git 插件标记为“检查中”；发现有远程更新后继续显示“检查依赖”。每完成一个插件的 Git 检查和本地依赖预检立即更新该行；全部候选解析完成后，再写回聚合 resolver 得出的跨插件冲突状态和最终摘要计数。
- 刷新完成后写入新的 `check_generation`，更新“上次检查完成时间”，并按最新状态重新排序。刷新取消或发生任务级失败时不得提升批次号，因此“全部更新”保持禁用；已完成行仍展示本次检查结果，未完成行显示“未检查”。

### 8.4 更新状态标识

“代码状态”和“依赖状态”必须同时使用图标/颜色和文字，不能只依赖颜色。状态列保持固定宽度，长原因放在“原因”列并提供完整 tooltip。

| 领域状态/任务状态 | 显示文字 | 建议视觉 | 行内操作 |
|---|---|---|---|
| `LOCAL_ONLY` | 未检查 | 中性灰圆点 | 无 |
| 正在执行 fetch | 检查中 | 旋转进度图标 | 无 |
| `UPDATE_AVAILABLE`、`AVAILABLE` 且依赖为 `NOT_CHANGED` / `SATISFIED` / `SAFE_TO_INSTALL` / `COMPATIBLE_UPGRADE` | 有更新 | 橙色向下箭头/状态标识 | 更新 |
| `UP_TO_DATE` 且 `UP_TO_DATE` | 已是最新 | 绿色对勾 | 无 |
| `LOCAL_CHANGES`、`LOCAL_AHEAD`、`DIVERGED` 且 `AVAILABLE` | 有更新，需手动处理 | 橙色更新标识 + 黄色警告图标 | 无 |
| `LOCAL_CHANGES`、`LOCAL_AHEAD`、`DIVERGED` 且 `UP_TO_DATE` | 已检查，需手动处理 | 黄色警告图标 | 无 |
| `DETACHED_HEAD`、`NO_UPSTREAM`、`NO_REMOTE`、`SUBMODULES_UNSUPPORTED` | 无法自动更新 | 黄色信息/警告图标 | 无 |
| `NON_GIT` | 非 Git 安装 | 中性灰图标 | 卸载 |
| `CHECK_FAILED`、`REPOSITORY_ERROR` | 检查失败 | 红色错误图标 | 无；下次刷新重试 |
| 正在快进 | 更新中 | 旋转进度图标 | 无 |
| 更新成功 | 已更新 | 绿色对勾；随后归一为“已是最新” | 无 |
| `UPDATE_FAILED` | 更新失败 | 红色错误图标 | 更新（允许用户重试单条） |

- “有更新”表示远程存在本地未包含的提交；它由 `update_availability == AVAILABLE` 决定。只有 Git 安全且依赖状态为 `NOT_CHANGED`、`SATISFIED`、`SAFE_TO_INSTALL` 或 `COMPATIBLE_UPGRADE` 的“有更新”行可自动更新；其他“有更新”行必须展示原因并禁用更新。
- 依赖状态显示“无需变更 / 已满足 / 可安全安装 N 项 / 可兼容升级 N 项 / 依赖约束不兼容 / 依赖需要降级 / 无法完整验证其他插件 / 核心依赖受保护 / 非标准依赖 / 需要源码构建 / 包含自定义安装脚本 / 预检失败 / 安装中 / 依赖就绪 / 安装失败”。当计划升级时，原因栏必须逐包显示 `当前版本 → 解析版本`、受影响插件和严格约束；`==`、`<`、`<=`、`~=`、`!=` 以警告标识呈现，但不单独禁用更新。批量任务中，任何被依赖阻止的行都必须直接显示“哪个插件的哪个依赖”导致阻止，例如 `插件 A 要求 foo==1；插件 B 要求 foo>=3；当前 foo==3，更新插件 A 会降级`；详情对话框展示同一结构化 `dependency_conflicts`，不得只显示批次级的“依赖冲突”。
- “全部更新（N）”中的 N 始终取完整数据集内、当前完整刷新批次的 `can_update=True` 数量，而非当前页面数量；摘要中的“有远程更新”可大于 N，差值必须计入“依赖阻止”或其他不可更新状态。
- 单条更新成功后，该行立即变为“已是最新”，全局可更新数量和按钮中的 N 同步减 1；N 变为 0 时禁用“全部更新”。
- 全部更新过程中依次显示“准备 wheel / 安装依赖 / 校验环境 / 更新代码 / 已更新 / 更新失败”，翻页后仍能看到已写回模型的结果。
- 安装预检与提交阶段在底部任务区依次显示“克隆插件 / 检查插件结构 / 解析全局依赖 / 等待确认 / 准备 wheel / 安装依赖 / 校验环境 / 写入插件目录 / 已安装”。安装成功后重新扫描，按默认排序显示新行；安装失败或取消时列表中不出现该插件。
- 对所有通过路径边界验证的现有插件行均显示“卸载”。卸载确认后的任务区显示“删除插件目录”，删除完成后该行消失；不会显示或猜测依赖清理状态。

### 8.5 分页规格

- 默认每页 20 条，可选 20、50、100；用户选择仅保存在当前页面会话，不写配置文件。
- 页码从 1 开始，显示 `第 X / Y 页，共 Z 个插件`。当 Z 为 0 时显示 `第 0 / 0 页，共 0 个插件`。
- 首页/上一页在第一页禁用，下一页/末页在最后一页禁用；任务执行期间允许翻页、搜索和筛选，但不允许触发新的刷新或更新任务。
- 数据处理顺序固定为：完整插件集合 → 状态优先级排序 → 搜索 → 状态筛选 → 分页切片。搜索或筛选条件变化、每页数量变化时回到第 1 页。
- 刷新导致总页数减少时，将当前页收敛到新的最后一页；不得出现空白的越界页。
- `PluginTableModel` 持有完整 `all_records`，并根据查询、筛选和分页参数计算 `visible_records`。行内操作必须按规范化后的插件路径查找记录，不能把可变化的表格行号作为插件身份。
- 分页只控制渲染行数。摘要数字、刷新进度、搜索基数和“全部更新”目标全部来自 `all_records`。

### 8.6 确认与提示文案

- 全部更新确认：`检测到 A 个插件有远程更新：其中 N 个可完整更新，M 个因依赖或仓库风险将跳过。将先按全部已安装插件的约束统一准备依赖，再快进插件代码；依赖计划：新增 {additions} 项、兼容升级 {upgrades} 项（{package_changes}）。已跳过插件：{blocked_plugin_reasons}。范围包含其他页面和当前筛选未显示的插件。更新后请重启 ComfyUI。是否继续？`。`blocked_plugin_reasons` 必须逐插件列出原因；依赖冲突至少列出包名、当前/计划版本、该插件的约束和冲突插件名，不得只给总数。
- 单条更新确认：`将更新插件“{plugin_name}”：先按全部已安装插件的约束准备依赖（新增 {additions} 项、兼容升级 {upgrades} 项：{package_changes}），再快进到 {target_short_head}。严格约束：{strict_constraints_or_none}。更新后请重启 ComfyUI。是否继续？`
- 安装预检确认：`将安装插件“{plugin_name}”到 {target_path}，仓库为 {sanitized_url}，锁定提交为 {target_short_head}。将按全部已安装插件的约束处理依赖：新增 {additions} 项、兼容升级 {upgrades} 项：{package_changes}。严格约束：{strict_constraints_or_none}。不会执行 install.py，更新后请重启 ComfyUI。是否继续？`
- 卸载确认：`将永久删除插件“{plugin_name}”的目录：{target_path}。Python 依赖、模型、缓存和其他目录不会删除。{local_changes_warning} 是否继续？`
- 依赖约束不兼容：`插件“{plugin_name}”因依赖“{package}”无法更新：当前 {current_version}，该插件要求 {candidate_constraint}，插件“{conflicting_plugin}”要求 {conflicting_constraint}；不存在可同时满足的版本，已跳过该插件。`。批量任务须对每个相关插件分别显示对应原因。
- 依赖降级：`插件“{plugin_name}”要求将“{package}”从当前 {current_version} 降至 {resolved_version}（约束：{candidate_constraint}），为保护现有环境已跳过该插件。{affected_plugins}`。`affected_plugins` 列出受该包影响的其他已安装插件及其约束。
- 全局索引不完整：`以下已安装插件的依赖无法静态识别，无法验证共享依赖升级后的兼容性，已阻止本次依赖变更：{plugins_and_reasons}`。
- 保护包冲突：`插件要求修改受保护的核心依赖，已阻止整个插件更新：{protected_changes}`。
- 非标准来源：`插件依赖包含 VCS、直链、本地路径或 editable 安装，启动器无法安全验证，已阻止整个插件更新。`
- 源码构建：`依赖没有适配当前环境的 wheel，需要源码构建，已阻止整个插件更新：{packages}`。
- 自定义脚本：`目标版本包含 install.py 或动态安装逻辑。启动器不会执行任意安装脚本，为避免插件更新后不可用，本次更新已阻止。`
- 安装地址无效：`仅支持以 .git 结尾的 HTTPS Git 仓库地址；请粘贴仓库 clone 地址。`
- 安装目录已存在：`目标目录已存在：{target_path}。启动器不会覆盖或合并已有插件。`
- 安装失败：`插件未安装：{reason}`。
- 卸载失败：`插件目录未完全删除：{reason}。已重新扫描实际状态；Python 依赖未被修改。`
- 依赖失败：`依赖准备或环境校验失败，插件代码保持原版本：{reason}`。
- ComfyUI 运行中：`ComfyUI 正在运行。为避免文件占用和运行版本不一致，插件更新、安装和卸载已禁用；请先停止 ComfyUI。`
- 本地修改：`检测到 X 个已修改、Y 个未跟踪文件；为保护本地修改，已跳过更新。`
- detached：`插件固定在指定提交，启动器不会擅自切换分支。`
- 无 upstream：`当前分支未配置远程跟踪分支，启动器不会猜测更新目标。`
- submodule：`该插件包含 Git submodule，v1 不自动更新以避免子模块版本不一致。`

## 9. 错误、日志与取消

### 9.1 错误码

服务层至少区分：`GIT_NOT_FOUND`、`NOT_A_WORKTREE`、`OUTSIDE_ROOT`、`TOPLEVEL_MISMATCH`、`UNBORN_HEAD`、`NO_REMOTE`、`NO_UPSTREAM`、`DIRTY_WORKTREE`、`DETACHED_HEAD`、`SUBMODULES_UNSUPPORTED`、`FETCH_TIMEOUT`、`FETCH_AUTH_FAILED`、`FETCH_FAILED`、`REV_LIST_INVALID`、`INSTALL_URL_INVALID`、`INSTALL_DESTINATION_EXISTS`、`INSTALL_CLONE_FAILED`、`INSTALL_PREVIEW_EXPIRED`、`INSTALL_STAGING_INVALID`、`INSTALL_FINALIZE_FAILED`、`UNINSTALL_PATH_INVALID`、`UNINSTALL_FAILED`、`DEPENDENCY_PARSE_FAILED`、`DEPENDENCY_GLOBAL_INDEX_INCOMPLETE`、`DEPENDENCY_INCOMPATIBLE_CONSTRAINTS`、`DEPENDENCY_DOWNGRADE_BLOCKED`、`DEPENDENCY_PROTECTED_PACKAGE`、`DEPENDENCY_NON_STANDARD_SOURCE`、`DEPENDENCY_SOURCE_BUILD`、`DEPENDENCY_CUSTOM_SCRIPT`、`DEPENDENCY_RESOLVE_FAILED`、`DEPENDENCY_DOWNLOAD_FAILED`、`DEPENDENCY_INSTALL_FAILED`、`DEPENDENCY_VALIDATION_FAILED`、`DEPENDENCY_ROLLBACK_FAILED`、`MERGE_FF_FAILED`、`CONTROLLED_ROLLBACK_FAILED`、`CANCELLED`。

界面使用映射后的中文摘要；日志可记录退出码、错误码和截断后的 stderr（最多 2,000 字符）。遇到 URL 时先调用脱敏函数。认证错误只提示“认证失败或无访问权限”，不可显示 Git 的凭据片段。

### 9.2 取消语义

- 取消是协作式的：当前 `fetch`、pip 下载/安装或 `merge --ff-only` 收到终止请求后返回 `CANCELLED`；尚未开始的条目均为 `skipped`。
- 依赖安装阶段取消时不得开始任何 Git 快进；按第 6.4.5 节恢复本批次已改动的依赖。Git 阶段取消时，已完整成功的插件及其共享依赖不回滚，尚未开始的插件保持旧版本。
- 安装预检阶段取消时终止 clone/解析、删除 staging，不修改 Python 环境；安装提交阶段在目录落位前取消时按第 6.4.5 节回退依赖并删除 staging。目录删除开始后卸载操作不可取消。
- 超时与用户取消不同：超时为失败，用户取消为取消；二者均不可自动重试。

### 10.3 验收标准

1. 对含本地修改、领先、分叉、detached、无 upstream 的插件，任何默认操作均不会改变工作区、分支或 `HEAD`。
2. 仅在“本轮检查证明 behind 且 ahead=0”且依赖准备与环境校验全部通过的干净分支上，执行一次 `git merge --ff-only <target_head>`。
3. 批量任务中单个仓库的网络/认证/更新失败不会停止后续符合条件的插件。
4. 用户取消后不再启动新 Git 操作，已经完成的更新不回滚且结果可见。
5. 所有 UI 更新发生在主线程，关闭页面后无遗留 worker 或 Git 子进程。
6. 现有 ComfyUI 本体稳定版/最新提交/强制更新流程和测试保持不变。
7. 无论插件数量多少，页面均展示全部插件并正确分页；非 Git 和异常插件不能因不可更新而从列表中消失。
8. “刷新”覆盖完整插件集合并逐项呈现是否有更新；“全部更新”覆盖所有分页和当前筛选未显示的可更新插件。
9. 依赖预检、下载、安装或 Git 前环境验证失败/取消时，插件 Git `HEAD` 保持更新前提交，且本批次改动过的依赖必须按 previous lock 离线恢复并回到更新前 `pip check` 基线；回退失败显示关键错误并停止自动处理。快进后的最终复验失败必须满足受控代码回退规则并且绝不能显示成功。页面显示具体依赖阻止/失败原因。
10. 一个插件只有在依赖满足、无新增 `pip check` 错误且 `HEAD == target_head` 后才显示“已更新”；不存在代码已更新但依赖待处理的正常完成状态。
11. 批量或单条更新均以全部已安装插件为全局约束集合，并对候选以 `target_head` 替换当前声明；存在冲突时跳过相关插件并显示冲突双方，不影响无关安全插件。非保护包可在完整集合仍满足时升级，绝不自动降级；更新顺序不会改变此结论。
12. 未安装 ComfyUI-Manager 的环境可完成所有功能；代码中不存在对其模块、API、CLI、配置和数据目录的依赖。
13. 安装仅接受用户指定的 HTTPS `.git` 地址：候选仓库先进入受控 staging，作为新项纳入全部已安装插件的全局依赖约束；只有依赖事务和环境验证成功后，才以原子 rename 落位至不存在的目标目录。任何预检、安装、校验、取消或落位失败均不留下新插件目录；在可回退窗口内也不留下本批新增依赖。
14. 卸载只在用户明确确认、ComfyUI 停止且路径重验通过后删除 `custom_nodes` 的一个直接子目录；不会删除 Python 依赖、模型、缓存、配置或任何仓库外文件。删除失败后停止操作并重新扫描实际状态。
